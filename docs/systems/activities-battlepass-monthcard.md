# BattlePass and MonthCard activity slice

BattlePass is NewActivity type 23 in `NewActivityConfig` rows 200, 201 and 9201. The 82976 common request carries claim, mark viewed, buy level and gift variants; 5013 stores the client-visible progress and reward markers. Pass 200/201 use item 132 as earned EXP currency, item 703 as premium entitlement, item 1020001 as a gift token, 60 levels and an ordinary currency-1 buy-level cost of 10 per level. Pass 9201 uses 920132/920703/920704, 30 levels, and an exported empty buy-level-cost value. Each level's award group comes from its own `BattlePassRewardConfig` row. Claim type 0 is free and 1 is premium (`LC_BattlePassHelper.lua`); a premium claim requires a real consumed 703/920703 token. The integrated cash-shop order/payment endpoints explicitly refuse purchases.

The server observes the configured EXP-currency balance when inventory changes and at login/tick. A positive balance change accrues pass EXP; a decrease never revokes earned levels. Required EXP is paid per next level and the remainder stays in `PlayerActivityBattlePass.exp`. Level and claim markers persist with grants in the same SQLite transaction. A new activity instance clears progress/claims and baselines its existing currency balance, so old currency cannot unlock a new pass cycle. This is **(inferred)** from the configured per-level `_iExpRequired` and the client's level/EXP fields; the extracted Lua does not establish the original server's progression transaction or season reset policy. The client helper's `CalculateLevelByExp` compares a total against each row even though all supplied pass rows have the same 2000 threshold, so it cannot itself define the server's multi-level accrual. Variant 9201's reward IDs refer directly to AwardConfig; 200/201 reward IDs go through MultiverseGroupConfig.

Premium and MonthCard are **owned item entitlements**, never implicit purchases. ProductConfig product 7 awards item 703; products 4/5 award 701/702. The server atomically consumes an owned entitlement token once and updates pass premium or MonthCard expiry. This conversion is **(inferred)**; the client confirms product award item IDs and reads the resulting activity state, but payment verification and original server conversion are not exposed. A pass gift spends owned 1020001/920704 and atomically delivers the configured premium item as a claimable mail attachment to the recipient. The gift UI opened by `LC_ItemHelper._useBattlePassGiftItem` and 82976 request are proven; ordinary mail delivery and one pending gift per recipient/activity are **(inferred)**. Mail claim activates the recipient's pass when its activity is live. The gift path checks configured tokens, recipient existence and pending mail; it does not assert friendship or a gift-day rule.

## Where pass EXP comes from

The client data grants no currency 132 at all (no AwardConfig, task or drop row), so the original server's sources are unknown. With `Ro3Emu:Pass:Play` on, this server uses its own design (**inferred** as a whole), in `NewActivityService.PassPlay.cs`:

| Source | Pass EXP |
|---|---|
| Daily challenges: 3 a day, drawn per role and game day from 5 (defeat 100 monsters, 50 in a party, reach 60 daily activity, clear a dungeon, complete 3 quests) | 300 each |
| Weekly challenges: all 7 (1000 monsters, 300 in a party, 300 daily activity, 5 dungeons, 3 MVP fights, 20 quests, play on 5 days) | 1000 each |
| Daily activity points (currency 5), watched after every award | 6 per point |
| Monsters | 3 each, up to 300 a day |
| Dungeon clear | 200, up to 5 a day |
| MVP fight (a settled participant) | 200, up to 3 a day |
| A story chapter's last main quest (8 chapters) | 500, once |

Multipliers: +20% in a party of two or more; double while the role has earned less than 75% of the season pace (60 levels in about six and a half weeks from the pass instance's start). Past the last level, every 2000 earned pays a bonus chest: the last level's free reward. The game day and week turn at 05:00 local time (Monday for the week). Progress is saved with the role; without a grant, every tenth change.

Pass I (200) can be forced open through `Ro3Emu:OpenContent:Activities` (its own condition is base level 99). Pass II (201) has the same condition and the same currency 132; on the original servers the two were consecutive seasons, but here every window stays open. With `Pass:Play`, Pass II therefore opens only once Pass I is at its last level (`PassTurnReached`, both in the gate and in the activity calendar), starts from the 132 balance it opens with instead of crediting it again, and from then on pass EXP from play and the bonus chests belong to Pass II (`OpenPass` takes the latest open pass). The novice pass 9201 (currency 920132, from base level 10, 30 levels) gains 300 for each main story quest (376 main quests, 60000 EXP needed). Its client rows are half done (Pass II's name, level rewards with no MultiverseGroupConfig row so the view showed empty slots, a level-50 wardrobe banner on a 30-level pass); the client hooks (`Ro3Emu.ClientHooks.NovicePass`) name it "Novice Pass" / "The First Steps", add the 60 reward group rows (type 0, AwardConfig of the same id) and hide the wardrobe banner while it is shown.

`Ro3Emu:Pass:FreePremium` (off by default) opens the premium track and its privileges without the 703 item. With the client hooks (`Ro3Emu.ClientHooks.PassChallenges`), `/pass` in chat or the "Challenges" button in the pass view (`PassButton`) opens the client's own season task panel with a "Daily" and a "Weekly" tab: the hook adds the 12 challenges as TaskConfig type-13 rows (ids 99130001-99130005 and 99130101-99130107, son types 139/138, under an activity row 99139 of its own), sends `PrivateMessageIds.PassChallenges`, and the server then adds the role's challenges to 5027 (running with progress, or delivered once paid). A client without the hook never opts in, so it never receives task ids it does not know; it gets the text answer on the marquee instead (`/pass`, `/pass week`). Completions and chapter bonuses are announced on the marquee for everyone.

MonthCard is NewActivity type 21, activity 199. Its 5054 state is the same `DBMonthCardInfo` nested in 5013. `MonthCardConfig` IDs 1001/1002 are 30-day cards with daily award groups 199006/199007 and a 143-day ownership cap. Owned 701/702 starts or extends the corresponding card at the realm-local civil-day boundary. `lastDays` is one higher than display days because `LC_ActivityParser_MonthCard.lua` subtracts one. An 82976 `GainMonthCardDailyAward` request may claim several distinct owned cards together; claim day and reward settlement persist atomically. A second claim on the same local day is refused, including after reconnect. On the next local day, the flag clears; after expiry, no further daily award is granted. Local civil-day rollover and 30-day expiry placement are **(inferred)** from the client's `lastDays`, `dayAward`, `expireTs` fields and configured `_iDay`.
