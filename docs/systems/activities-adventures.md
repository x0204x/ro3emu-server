# NewActivity adventure behavior

The activity book uses `NewActivityConfig` rows for playbook 101 and the default playbook 0. The server projects every configured row into 5013, with the configured time window and function gate applied before mutations. This file records the adventure-specific client routes and the server choices used where the exported client describes only the request and display behavior.

| Activity | Client route | Durable behavior |
| --- | --- | --- |
| Pre (102) | 82960-82962 | Donate item 1350001 for 50,000 progress per unit; accumulate global area/cycle progress in SQLite in the same transaction as the item cost; send totals and once-only milestone rewards from `SeasonPreProgressRewardConfig`. |
| Fragment Gather (105) | 82963-82967 and the 82976 oneofs | Daily asks, direct cross-role item transfer, craft, progress and ask completion use persistent role state. The sender's crystal, recipient's crystal and both activity blobs are one SQLite transaction. |
| Treasure (106) | Item action 304, 5064, interaction 4, 83251 | A map item selects a scene-editor hunt point, consumes the map and records the cursor atomically. Owner-visible NPC 21070002 can be interacted with in range. Configured weighted results grant a box or spawn a monster/boss; the fight's reward is settled once on death. The cursor restores a pending fight after scene load. |
| World Exploration (111) | 82976 fill and 83450 | Validate the phase's configured stage window, node, piece slot and item ID against `ExplorePhaseConfig`/`ExploreNodeConfig`; consume the piece and update 5013/5042 atomically. A slot cannot be filled twice. |
| Journey (112) | 82976 journey variants | Persist the configured act/node/travel/event graph and reward each completed node once. Dialogue alternatives use per-role Journey attribute and completed-act conditions; the selected branch removes its sibling candidates. Authored result actions modify attributes and Journey coin progress. Reported entry and panel state are durable. |
| Season Eve (117) | 82976 Season Eve variants | Persist each role's discovered clues, revealed notes, finished chapters, wish and claimed milestones. A cycle-keyed `DBSeasonEveInfo` holds global progress, discovery counts and recent completion barrage; discovery and chapter settlement update it in the same SQLite transaction as the role and reward. |
| Middle Season (107), Racing (108-110), Emblem (115), Top Guild (116) | 5013 schedule and entry projection | Expose their configured book window, state, function gate and entry metadata. Racing's `joinState` remains a participation value supplied by actual leaderboard play, rather than an activity claim. |

The direct route mapping comes from `data/msgtable.tsv` and `MG_NewActivity.proto`. Client calls were traced in `re/clientB/lua-src/Logic/Asset/LC_DAL_Season.lua`, `Logic/Season/LC_SeasonServer.lua`, `Logic/Asset/LC_DAL_ExplorationBigWorld.lua`, and `Logic/Journey/LC_JourneyService.lua`. The hunt's action 304, NPC and interaction constants come from `ItemConfig`, `ActivityConstant.lua`, `TreasureHuntMapPointConfig`, `TreasureHuntResultRateConfig`, and `TreasureHuntMonsterRewardConfig`; the client event handling is in `LC_DAL_SeasonTreasure.lua` and `LC_System_SeasonTreasure.lua`. IDs 82968-82974 in the message table belong to Flying Dragon requests and are handled by that feature.

The weighted treasure roll, hunt point choice, social gift eligibility, Journey transition timing and Season Eve clue validation are inferred server policies. They are bounded by the exported configuration, server clock, role/item ownership, the live scene and persistent once-only markers. Paid cash purchases are outside this activity implementation.

A finished World Exploration node offers its quest, `ExploreNodeConfig._iQuestID` (task type 21, claimed with 31205), and after it a different `_iFinishQuestID` (node 1033: 301006, then 301007). The client shows the node quest in its unlock tip (`UI_Sys_Season_MovementPlayPanelCtrl._createUnlockTipWidget`) and marks the node done once the finish quest is delivered; the server's offer is **(inferred)** from that (`TaskService.MiscTargets.cs`).

`LC_SeasonExplorationHelper.IsChapterInActivityTime` resolves phase `_kStartTime`/`_kEndTime` through `LC_SeasonHelper.GetConfigTimeStamp`; the authored type-4 tuples reference the start of season stages 101002/101003 plus an offset. The phase fill gate uses those exact stage boundaries. `GetChapterProgress` divides `totalRate` by 100 for the displayed percentage. The server calculates that field as 10,000 times filled note slots divided by configured slots in the phase (inferred contribution of note fill to chapter progress). The World Exploration wire test checks the first and second slots' basis-point totals, the delayed phase 102 opening, item ownership and reconnect replay.

Fragment 82963-82967 legacy responses have no result field in `MG_NewActivity.proto`. A refused direct request emits `COMMON_ERROR_NTF` (2) and a safe response without fabricated craft level or ask ID; 82976 returns its explicit `result`. Crafting updates `progressFinish` only after all five crystals are consumed successfully.

The successful craft reply uses level 1 (inferred). Season Eve discovery requires the authored map/point within 12 metres and the chapter's condition-based opening day. `SeasonEveChapterConfig._iCondition` resolves through `LC_ConditionList` type 16500 to offsets of 0, 86,400, 172,800 and 259,200 seconds from activity 117's start. `LC_ActivityParser_SeasonEve._processGetGlobalInfoResp` copies global `progress` to the panel's energy bar and milestones, `bulletInfo` to its barrage, and chapter `openTime` to chapter display. The four configured chapters each have seven ordered clues, require three discovered clues and use four note types. The client clue result widget renders `index` as a position 1-7 and `noteId` as an icon 1-4. The play panel sends all seven position-to-type choices. A first discovery durably reveals its position and type; repeats return the same clue result without adding another global discovery. The deterministic cycling assignment of types 1-4 across seven positions and comparison of the complete submitted pattern are **(inferred)** puzzle rules. Wrong patterns leave the chapter incomplete. A completed chapter grants its configured `_iAward` once and adds the configured `SeasonEveCompleteChapterProgress=500` to the shared cycle's capped `SeasonEveTotalProgress=1,000,000`; a completion also adds one bounded barrage record. Progress claims use `SeasonEveProgressAward` IDs/thresholds/rewards, not chapter IDs, and a wish needs total progress. The client reads the milestone IDs and thresholds in `UI_Sys_Season_EvePlayPanelCtrl` and gates the desire UI on total progress. The two-role wire test covers chapter opening, discovery counts, incorrect and correct notes, a chapter replay, global progress, recent completions and reconnect.

`ActivityConstant` also provides `SeasonEveProgressCheckPoint` as day-offset/target pairs `[(86400,100000),(172800,200000),(259200,300000),(345600,400000)]`, `SeasonEveProgressCheckInterval=60`, `SeasonEveProgressCheckCoefficient=[(5000,25000),(10000,15000),(15000,10000),(999999,8000)]`, `SeasonEveProgressCheckAddMax=500`, and `SeasonEveProgressFullTime=3600`. The **(inferred)** pacing policy linearly interpolates a minimum target from `(0,0)` through the authored checkpoints and holds the last target afterward. Each elapsed 60-second interval adds only a positive deficit, multiplied by the coefficient band selected from the current count of online roles eligible for activity 117 (the first band whose population ceiling includes that count), then capped by 500 and the remaining deficit. Chapter completions add 500 beyond this minimum without being reduced. Starting one hour before the configured activity end, the next Season Eve request makes progress the configured one-million total so the final milestone and wish become available. `DBSeasonEveInfo.lastCalcTime` is committed with each catch-up, making repeated requests and reconnects idempotent. The checkpoint interpolation, coefficient population meaning and final-hour settlement are inferred server policies; the UI consumes authoritative progress.

At activity expiry, the saved cycle is settled before its timestamps are refreshed, including when a role was offline until its next login. `SeasonEveWishConfig._iRewardId` names award groups 100085-100087 for a selected wish; `ActivityConstant.SeasonEveNoWishAward=100088` provides the fallback. The wish or fallback becomes a 30-day `MailConfig` 11450 letter. Threshold rewards in `SeasonEveProgressAward` that the role did not claim become one 30-day `MailConfig` 11451 letter. Both templates have `_iAward=0`; their attachments come from the corresponding award groups. Delivery eligibility is the role's recorded entrance into that cycle; expiry timing and bundling of multiple unclaimed thresholds into one letter are **(inferred)**. `MailService.DeliverActivityBatchAsync` commits both letters, the activity reset, the global final progress and `EveSettledCycleStart` in one SQLite transaction under the same StateLock/mailbox-gate order as an ordinary mail claim. Live expiry uses the activity ticker; the login hook settles an expired saved cycle before replacing its window. The wire test claims a wish attachment, checks replay refusal, and confirms separate chosen-wish/fallback and unclaimed-progress letters survive reconnect without duplicate delivery.

`LC_ConditionDefine` maps 15100/15101 to `LC_InteractCondition.CheckJourneyAttr` and `CheckJourneyDialogue`. The first checks a Journey attribute inside an inclusive configured range; the second checks whether any listed act was completed. `LC_JourneyHelperPartialAction.FindActIdByCondition` selects a matching pending act. `JourneyActConfig` node 101 begins at act 10101, offers alternatives 10102/10103, and advances through 10104. `PublicParamConfig.JourneyAttrInitial` gives each of the five attributes 100 initially. The authored 400 result tuples add an attribute delta, and 401 updates earned Journey coins and awards `PublicParamConfig.JourneyCoinItemId` (both result-action interpretations are inferred). NewActivityConfig row 112 has an authored level-999 open condition. The wire test supplies that eligibility in its controlled fixture while leaving all Journey progress server-owned.

`LC_JourneyStateHandlers.HandleIdle` maps action 406 to the mini-game UI and action 408 to the travel widget. The mini-game panels send `EJourneyCompleteType_Game` with the level ID encoded in the current 406 tuple; the server advances only that pending act and refuses an out-of-order level. The request contains the reported completion ID, so acceptance of a correctly ordered mini-game result is inferred. Action 408 belongs to act 10995 on node 103. During that act, the server projects a five-hour day from `JourneyTravelDayHour`; a configured travel choice consumes its `_iTime` cost and starts an event selected by `_kEventGroup`, `_iCondition` and `_iWeight`. This selection and the initial `curDay=1` are inferred. `LC_JourneyHelperPartialTravel`, the JobWidget and JobListWidget display the day, remaining hours and cost, and the End Today button confirms discarding remaining hours. `JourneyTravelTotalDay=7` bounds the cycle; the seventh End Today settles act 10995 and exposes dialogue 10996 (inferred transition). Repeating a travel increments `completeTravel.count`, which `LC_JourneyHelperPartialReview` reads for the chapter review.

The EventPanel selects a configured `_kBtn` child; the EventResultPanel confirms `eventInfo.eventId`. A travel or action 402 selects a weighted event from the configured group whose attribute condition passes. Enter actions 400/401 update attributes and coins and expose attribute deltas through `eventInfo.attrChange`; result action 402 chains to its next group (inferred server sequencing). While an event is pending, another travel or End Today is refused. Branch requests are limited to the current event's `_kBtn` IDs, and a finished event can occur on later travels with an incremented `completeEvent.count`. The wire test advances through the first dialogue node, the three authored mini-game levels and the travel node, then checks event branches, hours, repeat counts, day rollover and cap.

Attribute changes also send 82977 `JourneyAttrChange` with the actual committed delta. `UI_Sys_NoviceChallengePanelCtrl._onJourneyAttrChange` adds it to the existing asset value for the animation, so the notification follows the transaction and precedes the 5013 update (inferred wire ordering). Action 400 samples the inclusive configured delta range uniformly; action 401 similarly samples the configured coin range (inferred distribution).

Journey's authored boss acts use action 407 in `JourneyActConfig`: acts 10111 and 10114-10117 point to DungeonConfig 8100002 and 8100004-8100007. `NpcLevelPointRespawnConfig` pairs each map with NPC 81000002/04/05/06/07 at scene-editor point 26 in `sc_pm_newbee_001_dg01_sceneeditor`. These are the encounter actors for entry and restart.

For the projection-only rows, the supporting client evidence is `LC_ActivityParser_Racing.lua` (copies `joinState`) and the Season/ThreeDays panel models and rank widgets (index `joinState` by `LeaderBoardType`). Their activity rows supply time limits, book ID, gate, entry type and UI resources. Generic reward requests in `LC_ActivityServer.lua` are the seven-day reward path.
