# Mailbox implementation and evidence limits

The current client uses `MailService` micro RPCs for list, content, read, delete and group sync, plus game message 31602 for attachment claims (`LC_DAL_Mail.lua`). Role ownership comes from the verified micro account and the selected game role. `Uid` only confirms that selected role. Mail is stored in the role's SQLite `mailbox` blob. Server delivery is available for offline and online roles through `MailService.SendRawAsync` and `SendTemplateAsync`; the GM smoke command is `!mail <title> [item count]`. A successful delivery pushes `newMailNotice` or `newGroupMailNotice` to an online micro session. Login pushes a notice for persisted unread or read-but-unclaimed mail.

The canonical `Letter.ContentParams` persistence is protobuf `LanguageData` bytes serialized as JSON base64. The Lua mail DAL decodes `content_params` as `romsg.LanguageData` and reads each parameter's `tp`, `intParam` or `strParam` (`LC_DAL_Mail.lua:1799-1824`); auction integer placeholders therefore remain integers on the wire. Mailbox loading accepts the earlier market `string[]` JSON shape and converts it to string-typed `LanguageData`, while earlier auction base64 bytes are retained unchanged. Saving a loaded mailbox writes only the canonical base64 shape. The retired `market_record` migration likewise converts its string array to the canonical form. A letter can carry configured entry/count/bind attachments, exact `InvItem` instances, and long currency amounts together; claim persists all grants and the claimed flag in one transaction. The shared mailbox semaphore is acquired once for any multi-recipient auction transaction.

`SendTemplateAsync(role, templateId, attachments)` retains the caller-supplied list, including an explicit empty list for source-specific compensation. The overload without attachments resolves nonzero `MailConfig._iAward` through `MultiverseGroupConfig` and playbook-specific fixed `AwardConfig` triples **(inferred template execution)**; it refuses conditional, pooled, restricted, bound or expiring award rows. Template 1024 without an explicit list therefore provides its configured 5,000 Zeny. The configured award does not prove the amount of any actual resent compensation; its source must supply the exact attachment list. `SendTemplateOnceAsync` also records a source delivery key and source state in one transaction, accepting earlier `SourceKey` mailbox JSON while writing `DeliveryKey` thereafter. Ordinary APIs use entry/count/bind grants, without arbitrary item-instance metadata. Virtual Base/Job EXP entries 100/101 are applied to progression atomically with the claimed flag through CharacterService. The transactional market API additionally accepts complete `InvItem` snapshots, long currency amounts and `LanguageData` content substitutions; the same claim handler preserves binding, rolls, enchantments, expiry, lock state and string attributes. Current trade/stall producers use only configured currencies 1 and 2; the internal market currency argument is not an EXP-grant API. Unknown template IDs and unsupported `_iTimerMethod` values without explicit expiry are refused by the ordinary template API; market asset delivery chooses no expiry. `_iRead`, `_iType`, and `_iFullReceive` are not interpreted; their service behavior is unproved.

Unix seconds for `CreatedTime` and `RemoveTime` follow `Lua_TimerManager.lua:706-717`, `Lua_TimeHelper.lua:12-34,471-508`, and `UI_Sys_MailListWidgetCtrl.lua:187-270`: system time is seconds and the mail UI divides the expiry delta by 86400. **(inferred)** `MailConfig._kTimes` is a number of days when `_iTimerMethod=0`; raw mail defaults to 7 days without an attachment or 30 days with one, following `PublicParamConfig.MailTextTimeMax` and `MailAttachmentTimeMax` as day candidates. At `now >= RemoveTime`, expired mail is removed from the durable mailbox on the next mailbox access or delivery; this includes unclaimed attachments. `DateTimeOffset.MaxValue` explicitly creates no expiry. There is no background sweep.

Lists sort by descending `CreatedTime` and `MailId` as in `LC_DAL_Mail.lua:715-735`. **(inferred)** IDs are numeric strings from UTC ticks, advanced past the persisted per-role `NextId` so they remain monotonic after restart. **(inferred)** `Start` then a maximum 150 rows are applied; `Limit=0` is treated as 150. The service retains all delivered active rows, so older rows stay durable and can be requested with a larger `Start` or appear after deletion. The client UI says full categories cannot receive new mail; the original server's queue/rejection rule remains unproved. Category 2 has no sender path. Deletion is all-or-nothing and refuses a row with unclaimed attachments, following the client UI. **(inferred)** `syncGroupMail` checks active System/Guild rows for unread or read-but-unclaimed mail and pushes `newMailNotice` before its ordinary ACK, recovering a notice lost while the micro gate was disconnected and the game role stayed selected. It does not alter row flags. The client applies a 300-second reconnection throttle before calling `syncGroupMail` (`LC_System_Mail.lua:83-118`), so this is recovery on sync, not an immediate reconnect guarantee. Group broadcast composition is not implemented.

**(inferred)** Claims commit all configured, exact-instance, currency and virtual Base/Job EXP grants of a letter with its claimed/read flags in one SQLite transaction. Exact instances receive fresh bag GUIDs without rerolling or merging their metadata. A repeated, foreign, expired, empty, or capacity-blocked claim returns a nonzero result with no IDs; the client dispatches nonzero results to its generic error handler. Duplicate IDs within a request are deduplicated. The exact request-to-error-code mapping, bag-capacity refusal, and choice of the last refusal when every requested row fails are **(inferred)**. Bulk replies contain only successfully claimed IDs; partial bulk success uses result 0 and skips refused IDs. A failed network sync after commit cannot reopen a claim. The protobuf attachment bytes and empty repeated-field behavior still require a live client probe.

Trade and stalls deliver through the canonical service in the caller's SQLite transaction, so escrow consumption and mailbox insertion commit or roll back together. A shared mailbox semaphore protects blob read/modify/write against ordinary delivery, micro updates and claims. Lock order is market gate, ordered session state locks, mailbox gate, then SQLite; ordinary mail never takes a session lock while holding the mailbox gate. Only post-commit deliveries notify recipients. The retired `Game/MarketMail` claim handler and `Micro/MailService` adapter are removed. Legacy market mail is migrated atomically at market-store initialization, preserving claimed flags and attachment metadata before deleting the old rows. Market asset letters retain their existing nonexpiry policy (`RemoveTime=0`); ordinary-mail expiry above is unchanged. See [trade-stalls.md](trade-stalls.md) for template evidence and integration details.

The current mail DAL registers no player-to-player send request (`LC_DAL_Mail.lua:72-120`); its five request methods cover list, content, read, delete and group sync. The Personal list therefore remains empty. Server callers can deliver System (1) or Guild (3) rows. Existing function sync 5056 opens the mail UI through FunctionConfig 47/4701; item/currency changes after a claim use 5009, EXP progression uses 5066, **(inferred)** the claimed goods are shown by a ManifestTypeFloat 31322 notice in which each new piece of equipment is its bag item (GUID, appraisal, score), so `LC_EquipmentHelper.CanFastEquip` can offer to wear it as it does for a drop, and there is no mailbox AUTO_SYNC dataset. The delivery code does not consult MultiverseSchedule.

Other systems provide their actual compensation rewards, for example:

```csharp
await mail.SendTemplateAsync(roleId, 1024); // resolves configured fixed _iAward
await mail.SendTemplateAsync(roleId, 1025, [new MailService.Attachment(itemId, count)]); // source decided condition
await mail.SendRawAsync(roleId, "Maintenance compensation", "Thank you for waiting.",
    [new MailService.Attachment(2, 100)]);
```

## Tests

`MailTests` and `MarketMailTests` cover the real micro/game wire, SQLite persistence, single/bulk/replayed claims, read/delete, template 1024 and offline template 1020, configured `_iAward` templates, expiry, ownership, malformed inputs, bag/currency refusals, virtual EXP level-up/rollback/replay, source-owned transaction rollback, legacy `SourceKey` migration, concurrent delivery, both historical mailbox JSON formats, typed localization on the micro wire, exact market instance attributes, bound auction grants, combined long currency, capacity refusal and recovery, and restart. Invalid attachment refusals cover unknown entries and nonpositive counts. The reconnect test uses a new verified micro connection while the original game role remains selected; it proves reconciliation, not an actual transport outage.
